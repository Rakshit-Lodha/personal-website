What Is a Harness, Anyway?

Via Theo (t3.gg) — flagged for the paper, read in full

Theo is tired of explaining the word, so he wrote the explainer nobody else had bothered to write — and it is the single clearest thing in this week’s pile on the most overloaded term in the agent economy. The setup is disarmingly simple: humans never use computers directly. You use an interface — a terminal, a website, an app — rather than writing unique code per task. Nobody opens Chrome and thinks about the code underneath. An LLM has the same problem in reverse: left alone, it can only generate text. To do anything real, it needs an apparatus around it — tools (read_file, edit_file, bash, search), a custom text syntax for calling them (something like <read_file name="README.md">), a system that parses that syntax and actually runs the code, a way to feed tool output back to the model, and a catalogue of the available tools with descriptions. That whole apparatus is the harness.

Theo’s mental model: an agent is what happens when you combine a harness and an LLM — most “different agents” are just different harness configurations.

The second move is the one that will save you from half the marketing you read this year. Is Claude Code a harness? Kind of. Claude Code has two parts: the interface (the terminal TUI, the desktop GUI) and the harness (the Anthropic Agent SDK running underneath; ChatGPT and Codex sit on the Codex App Server the same way). The harness is rarely exposed to humans directly — which is why it is also the part everyone reuses. The Cursor harness powers Grok Bot. The Anthropic Agents SDK and the Codex App Server power T3 Code. Pi powers OpenClaw. When someone launches “a new agent,” Theo’s test is simple: which harness did they configure, and what did they change?

The kitchen metaphor does the rest of the work. A harness is like a kitchen: no kitchen has every tool every chef needs, so the good ones let you bring your own. Codex and Claude Code ship with many tools; Pi is deliberately minimal. And — this is the line to underline — neither the human nor the LLM can see or touch the tools directly: the harness is what exposes them to both. Then MCP arrives to complicate the picture, and Theo makes it legible in one contrast: tools are “run code here to do a thing,” MCPs are “make an API request somewhere else to do a thing.” Chrome extensions are like tools (they run locally); MCPs are like websites (you only need the URL). The most common MCP use case, he notes, is just exposing data — emails, site analytics — and T3 Code’s trick is exposing its custom functionality as an MCP, a cookbook for the kitchen, rather than building its own kitchen at all.

“Neither the human nor the LLM can see or touch the tools directly — the harness exposes them to both.”— Theo, “What is a ‘harness’?”

Why lead the paper with a vocabulary lesson? Because the saves this week keep circling the same insight from different altitudes. Theo’s own follow-up post says Meta’s Muse Wonder Full is “probably the most impressive coding model I’ve used since Sonnet 4.5” for orchestration work — long-running multi-step tasks without getting lost. Read through the harness lens, that is a claim about the chef getting better at working inside the kitchen: a model that holds its thread across dozens of tool calls changes what a harness can be trusted with. Two editions ago this paper covered hnshah’s “harnessification of software” essay; this is the field manual for that thesis. If the durable unit of software is shifting from features to responsibilities, then the harness — the apparatus that lets a model be responsible for something — is the layer worth understanding first.

Learnings

  • Separate the interface from the harness before you evaluate any “agent.” Ask: whose harness is it, what tools does it ship, can you bring your own, and what changed in the configuration.
  • MCP is not a tool; it is a cookbook. Tools run code locally, MCPs make requests elsewhere. Most MCP value today is just exposing data (emails, analytics) to the kitchen.
  • The chef is catching up to the kitchen. Models that survive long multi-step orchestration without losing the thread (Theo’s read on Muse Wonder Full) are what let harnesses take on real responsibility.
Takeaway — Every “new agent” launch this year deserves Theo’s two questions: which harness, and what did they change? The answers are usually more interesting than the announcement.

Dessa: The Model That Learned to Talk by Listening

Via Ragavan Thurairatnam · Jack Dorsey · Shweta Bharadwaj · Linus Ekenstam

Block’s in-house AI lab announced Dessa on Thursday, and the claim is the kind that sounds impossible until you hear the mechanism: a full-duplex speech-to-speech model trained from scratch on nothing but human conversation — no text data, no pretrained language model underneath. It takes in audio and puts out audio, simultaneously. It learned, from real conversation, when to cut in and when to backchannel with a little “mm-hmm” to show it is following. It natively hears and produces emotion, sarcasm, laughter, a frustrated sigh, a voice cracking with sadness. Ragavan Thurairatnam, the lab’s lead, calls it “a GPT3 moment for speech.” Jack Dorsey, who the team reports to: “Voice is the most natural way to interact with intelligence… talking with it feels like talking with a person — full of emotion, nuance, pauses, and a natural cadence.”

The training story is the thesis. Block says Dessa learned language the way a child does — “Babies learn to talk without ever seeing a word written down. We wanted to see if a model could too. It can. It’s just very hard.” — from “hundreds of times fewer words” than the text corpora LLMs see, on a single NVIDIA GB200 NVL72 rack (serious compute, but a fraction of a frontier text cluster). The payoff is what gets lost in the standard voice pipeline: every conventional assistant flattens your speech into text, runs it through a language model, and turns the answer back into speech — and in that flattening, timing, tone, and all the non-text signals get discarded. Dessa keeps them because it never had text to begin with. Inference runs faster than real time, so replies land without the awkward pause, and the whole thing runs on a MacBook Pro M4 Max or better — no cloud required.

“The real uncanny valley isn’t clankers sounding like people. It’s that we’ve forgotten what a mid-IQ, average-articulation conversation even feels like.”— @shwetzzalmighty

Shweta Bharadwaj’s reply is the observation of the week: every bot we talk to is a 140-IQ language model with perfect grammar and no “uhms”, so we have forgotten what a normal person sounds like. Linus Ekenstam’s verdict: OpenAI’s voice mode just got “slapped”, and the Turing test for voice is solved. Ashish Singh calls it the biggest voice-AI breakthrough since GPT-4o’s voice mode. The team is honest about the rough edges — Block’s own demos include Dessa mistaking a speaker for someone named Ronaldo, and one write-up calls the exchanges “like talking to an awkward new friend” — but the safety framing is worth sitting with: “AI keeps gaining power and independence, and it’s still nearly deaf to the emotion in our voices. Imagine being in serious pain while a voice AI has no idea and just keeps going.” Dessa is, among other things, a bet that hearing is a safety problem. Access is a public waitlist at block.xyz/dessa, with early access going to AI safety researchers first.

Learnings

  • The pipeline is the product. Speech→text→LLM→speech discards exactly the signals that make conversation human. Removing the text bottleneck is an architecture insight, not a bigger-model insight.
  • Data efficiency is the sleeper stat. “Hundreds of times fewer words” on one rack — the speech-native route may be cheaper than the text route ever was.
  • Local inference changes the trust equation. A voice model that runs on your MacBook sidesteps the cloud-latency and privacy objections in one move.
Takeaway — Watch for the inversion: the best voice interface may not come from the labs with the best text models. It may come from whoever throws the text away.

Kimi K3.1 Pro: Three Points Off the Frontier, Weights Incoming

Via Kimi.ai (Moonshot AI)

Moonshot AI launched Kimi K3.1 Pro on Friday, and the independent numbers are the story: 55 on the Artificial Analysis Intelligence Index — fourth overall, three points behind Claude Opus 5.5’s 58, and eleven points above Kimi K3. The weights land by November 4th, at which point it becomes the highest-scoring open-weights model available — and the gap between the best open model and the best proprietary one compresses from twelve index points to three. The skeleton is unchanged from K3 (2.8 trillion total parameters, 104 billion active in an MoE design, one-million-token context, text plus image), but the post-training compute was turned up enormously — and almost all the gains sit in agentic work, which is where the money is.

Two years of received wisdom — open weights trail the frontier by a generation — redrawn in one post-training pass. Figures: Artificial Analysis launch analysis, Oct 2026.

The details that matter for builders: Moonshot deliberately stripped cyberattack training data out of the model so the open release won’t push the frontier of offensive hacking; the Highspeed variant runs two to three times faster for interactive work; both are live now across the Kimi app, Kimi Work, Kimi Code and the API, with prices a third lower than K3’s. On Moonshot’s own hallucination stress test the claim-level error rate fell from 23.4% to 8.3%. The colour around the launch is already mythic — one widely-shared post claimed an unnamed top US law firm “cut off Claude and installed Kimi” (unverified), and a Dario-Amodei-emergency-session rumour picked up a Community Note. Strip the mythology away and the durable fact is the index score: near-frontier capability at open-weights economics, eleven points of it bought with post-training alone.

Learnings

  • Post-training is the new pretraining. Eleven index points with no architecture change — the RL stack, long-context inference and sandbox infra did the work.
  • Agentic benchmarks are the scoreboard now. GDPval, Terminal-Bench, AutomationBench — the gains cluster where agents do economically valuable work.
  • Open weights at 55 points reset the build-vs-buy math for anyone currently renting frontier capability by the token.

The 39 Most Obvious Startup Ideas Right Now

Via Greg Isenberg

Greg Isenberg dropped a numbered list of 39 startup ideas this week, and the list is more interesting as a pattern than as 39 pitches. The pattern: every incumbent category is getting an agent-native twin. Zestimate for company data. Google Analytics for agents. Y Combinator for one-person companies. Okta for agents. Marie Kondo for company data. FICO for agents. Geico for agents. Datadog for agents. Twilio for agents. Upwork for agents. ESPN for AI. Shutterstock for robot training videos. Credit Karma for what AI knows about you. Norton for AI scams. And twenty-five more in the same vein.

Isenberg’s list, compressed: the agent economy needs its own identity, credit, analytics, insurance and marketplaces.

Read it next to Theo’s harness piece above and the economics sharpen. If an agent is a harness plus an LLM, then every agent is a customer that needs the same infrastructure humans needed — and the incumbents were built for eyeballs, not API calls. The sharpest entries on the list are the ones that treat the agent as the buyer: analytics for agents (who watches what the harness did?), FICO for agents (which agents are creditworthy counterparties?), Norton for AI scams (the attack surface is machine-speed now). The meta-lesson of the list is the one Isenberg keeps returning to: the biggest opportunities sit one layer below the thing everyone is excited about. The gold rush isn’t agents. It’s the picks and shovels the agents need.

Learnings

  • Agents are a customer class, not a feature. Every “X for agents” idea is really “rebuild X for a buyer with no patience and infinite scale.”
  • Trust infrastructure comes first in a machine-speed economy. Identity (Okta), credit (FICO), insurance (Geico), scam protection (Norton) — the unsexy layer is the moat.
  • Your data exhaust is someone’s product. “Credit Karma for what AI knows about you” is the consumer version of the same thesis.

The Engineer Who Stopped Writing Code

Via Tanay Kothari, co-founder & CEO, Wispr Flow

“I’ve been writing code since I was 10. I’ve barely written a single line in the last year. Claude or Astra writes it. I read it and make sure I understand it.” Tanay Kothari’s post is the most honest account in this week’s pile of what the engineer’s job has actually become. For a couple of months, he writes, it hurt — a lifetime spent getting good at writing code, and the skill felt useless. Then the reframe landed: the years of coding still matter, because engineers can now use their experience to guide a lot more work at once. Today every engineer at Wispr runs five to ten agents in parallel, and they are shipping faster than ever. “I don’t think anyone feels sad about not writing code anymore.”

“Every engineer at Wispr runs 5 to 10 agents in parallel, and we’re shipping faster than ever.”— @tankots

The mechanism is the identity shift. The scarce skill moved from writing the code to reading it — reviewing, understanding, directing — which is exactly what a decade of writing code trains you for. The engineer becomes the manager of a small fleet: five to ten agents, each doing the typing, with human judgment as the scarce resource on top. It pairs uncomfortably well with this week’s hnshah-adjacent grok-bot mania and the harness thesis: the interface changed, the harness changed, and now the human’s job inside the loop is changing too — from producer to conductor. The grief phase (“for a couple of months that really hurt”) is worth naming plainly, because every experienced engineer reading this has felt some version of it, and Kothari’s answer is that the feeling passes when the leverage arrives.

Takeaway — If your engineers are still measured by code written, you are measuring the wrong thing. Measure what they can direct.

WTH India! — And What Comes After Convenience

Via Vaibhav Domkundwar, founder, Better Capital — two essays, read in full

Vaibhav Domkundwar published two essays this week that read as a matched pair — a diagnosis and a prescription. The diagnosis is “WTH India!”: India’s “normalized dysfunction” — things unnecessarily complicated, inefficient or outright absurd that have become so routine people accept them as the price of living or doing business here — is a hunting ground for company building. The prescription is “India IRL”: after two decades of making consumption accessible and convenient, the next multi-decade opportunity is making the actual experience of living better. Together they are the sharpest India consumer thesis in this paper in months.

The WTH thesis starts from a pattern: the person who needs the outcome does far too much of the work. Receiving an overseas payment means navigating forms, declarations, signatures and regulatory follow-ups — “the customer is effectively doing the institution’s work.” Renovating a home turns the owner into a coordinator of contractors and budgets. Running a small business drowns the owner in reconciliations and compliance. Each maps to a business: cross-border financial services, a trusted homeowner representative managing the entire outcome, managed financial operations, patient-side care coordination, end-to-end property management. But the line that matters most draws a boundary between two kinds of products: most products improve individual steps — better forms, faster approvals, dashboards — and sometimes the customer doesn’t want a better way to manage the process at all. They don’t want to manage the process. The homeowner wants the home completed to agreed quality, budget and timeline. Trust replaces supervision; reliability replaces follow-ups; accountability replaces coordination.

Domkundwar’s move: stop at “better tools” and you have a feature; go to “own the outcome” and you have a company.

Two ideas in the essay deserve underlining. First, the hidden cost: people get so good at workarounds — hiring intermediaries, supervising harder, baking follow-ups into routine — that the effort becomes invisible, and the hardest cost to see is the activity that never happens. Removing friction doesn’t just ease an existing activity; it can enable activity that wasn’t happening. Second, the discipline: “A problem worth solving isn’t automatically a business worth building.” WTH India is explicitly a thesis for finding problems, not selecting businesses — start from the friction, imagine a fundamentally better experience, and let the model come later.

“India IRL” then asks what comes after the convenience era Better Capital helped pioneer (they were early on quick commerce). The last two decades made things accessible, affordable and convenient; the next question is “What human experience can I make dramatically better — starting from the human, not the product?” The coffee worked example makes it concrete: not another brand or café chain, but starting from why people drink coffee — taste, ritual, energy, the pause, the environment — and imagining completely different coffee experiences brought to people rather than demanding they come to you. Crucially, it must not mean only luxury: the bigger opportunity is making previously inaccessible experiences mass-market — the fitness experience without the expensive trainer, personal care beyond premium salons. And the technology may be near-invisible: “Technology may make the business possible. The human experience is what makes it valuable.” The difficulty of physical delivery — people, locations, training, expectations — is the moat.

“Because ‘that’s just how things work in India’ doesn’t have to be the end of the conversation. It might just be the beginning of a really good business.”— @vaibhavbetter

Learnings

  • Hunt friction, not categories. Start from where people absorb complexity involuntarily; the business model comes second.
  • Outcome ownership beats tool improvement. The customer doesn’t want a better way to manage the process — they want the result.
  • Count the never-attempted. The largest opportunity in any friction is the demand that doesn’t exist yet because the experience is too hard.
  • Start from the human, not the product. India IRL’s question works on any category: what experience, for whom, in which moments of their life?

A Knowledge Base Built for Two Readers

Via Sergii Makarevych — article read in full

Nearly every published knowledge-base design serves only the model, Sergii Makarevych argues — but a project knowledge base has two readers: the AI coding agent that acts on what it finds, and the engineer who must understand the system. His article is the most rigorous thing in this week’s pile: five operations over one tree of Markdown files — Store, Create, Update, Retrieve, Teach — where everything is chained so that when a source changes, every page built on it is rebuilt in the same run. It is, not coincidentally, a design for the harness age: the knowledge base is the context the harness feeds the chef.

Makarevych’s design, with the measurements that make it more than a style guide. Every figure is from the article’s cited studies.

The design repays a close read. Store keeps three folders strictly separate: raw sources (captured exactly as fetched, never edited), facts (each chunk one fact — the original span word-for-word beside a rewrite that reads on its own), and artifacts (everything the model wrote). Create runs a fixed six-step pipeline with a guardrail at every page — a script check that every link resolves, plus one model call asking whether the page says anything its facts don’t. Update is the heart of it: when a refetched source’s hash changes, a script walks the links backward and rewrites every dependent artifact in the same run, nearest the change first, stopping early when a rewritten page means the same as before (a “same-meaning stop” borrowed from incremental build systems). Retrieve is progressive disclosure through short index files — and the article’s most practical finding: the project index must be the agent’s first read, not a skill it chooses to invoke, because Vercel measured an always-loaded 8KB index passing every eval case while the same content as an on-demand skill passed 53%. Teach serves the second reader: top-down reading for newcomers, bottom-up from a ticket-named chunk for experts.

The sharpest line in the piece is about the spec: “The spec is the one input I control, and in the measurement it moved success by about a third.” Specs are written only when a feature is to be implemented, with every critical statement validated against and linking to a fact — and agents given full docstrings resolved ~89% of tasks versus ~56% with bare signatures. The whole design is an argument that context engineering is an engineering discipline: versioned inputs, per-stage gates, scripted updates, measured retrieval. It is the natural companion to this edition’s lead story — Theo defined the harness; Makarevych designed what you feed it.

Learnings

  • Check at every stage, not at the end. Per-stage gates cut surviving errors from 58.4% to 16.2%; a final check alone gained 2.3 points.
  • Update by inputs, never by date. Rebuild-by-recorded-inputs kept 30 of 30 workflows current; age-based checking let all 30 go stale.
  • The index must be the first read. Context the agent has to choose to fetch is context the agent won’t fetch.
  • Organise, don’t condense. Condensing rewrites cost up to half the answers; organised-but-uncondensed stores cost nothing.

How to Build and Run an Army of AI UGC Accounts

Via Tibo — article read in full

Tibo’s article is the most operational thing in this week’s pile: a complete system — with twelve copy-ready prompts — for replacing rented human UGC with owned AI creators. The premise is economic. UGC works because it doesn’t look like an ad, but running it breaks in four places: it’s an operations job (finding, briefing, chasing, paying creators who rotate), you pay per video (and testing hooks is the whole game, so per-video pricing is what kills testing first), it’s slow (briefs and edit rounds post last week’s format into this week’s feed), and you don’t own any of it (the face, account and audience belong to the creator; usage rights expire). Three things changed the math: AI faces now stay consistent across hundreds of videos, you can search what’s already working instead of guessing, and agents can run the whole loop — search, script, render, schedule — so one person can run what used to need a small team.

The design principle is the part worth stealing even if you never touch AI faces: design the creator from the buyer, not from the product. The example builds four creators for a vitamin C serum — Priya (wellness, India), Jess (travel, USA), Liam (outdoors, Australia), Layla (lifestyle, Dubai) — and none of them is “a skincare creator.” Each gets a bible (speech patterns, values, habits, running jokes, what they’d never say), a locked face with one distinctive detail for thumbnail recognisability, and twenty topics — at least fifteen unrelated to the product. The rule is blunt: a creator who only talks about the product is “an ad with a face,” and the non-product videos build the audience the product videos are for. The product appears inside the creator’s life for exactly one beat, the way a real person mentions something they use — “if it sounds like being paid, it’s wrong.”

“One creator is a channel. Three or four of them, each speaking to a different kind of buyer, is the army.”— Tibo

The loop itself is pure harness thinking: the agent is the brain, every tool is swappable, and the daily run reads each creator’s file, picks an unused topic, searches viral references, remixes the winner’s structure (never its words), renders with the saved character, and schedules — never publishes — at least 24 hours out. That 24-hour review window is the load-bearing human decision: you scan the queue once a day and kill anything off, staying in control without becoming the bottleneck. Weekly reviews rank by watch-through and saves, not views. And when a creator flatlines for three weeks, the diagnosis is counterintuitive: “the instinct is to post more. usually the persona is the problem, and more posts of the wrong person just gives you more of the same result.”

Learnings

  • Own the face, the account, the audience. Rented creators reset you to zero; owned creators compound.
  • Remix structure, never words. Keep the winning hook type, pacing and length; change the setting, story and language.
  • Schedule, don’t publish. The 24-hour review window is where human taste stays in the loop without becoming the bottleneck.
  • When it flatlines, fix the persona, not the volume. More posts of the wrong person just give you more of the same result.
Takeaway — The playbook generalises: the agent is the brain, tools are swappable, the human owns the review window. That’s a harness, and it works on anything with a loop.

If I Had 30 Days to Change My Life

Via Mayank — article read in full

The most-saved life-advice piece in the pile is refreshingly un-mystical. Mayank’s 30-day guide is a systems manual, not a motivation poster: audit reality on day one (health, work, environment, relationships — “you cannot fix a problem you refuse to look at”), pick exactly three measurable priorities, fix mornings before fixing the day (consistent wake time, no 5 AM fetishism, one protected 30-minute focus block), and design every habit with a low starting minimum — fifteen minutes to open the postponed course, workout clothes laid out, the next physical action defined. The week-by-week roadmap (control the basics → build consistency → increase capacity → evaluate) is less important than the two recovery rules: when a day goes badly, name what broke, do one useful thing, and make tomorrow easier — and “consistency isn’t never falling off track. It’s learning how to return without turning every setback into a personal crisis.” The closing line belongs on a wall: “A better life is rarely built through one extraordinary decision. It’s built through ordinary decisions that you repeat long enough for them to change your circumstances.”

Start With Possibilities, Not Problems

Via Aakash Gupta · Ankit Shukla (HelloPM) — video captions sampled, post read in full

“Product management teaches you to start with the problem. @AnkythShukla thinks that’s exactly why AI projects go nowhere.” Aakash Gupta’s summary of his long interview with HelloPM founder Ankit Shukla contains the sharpest diagnosis of stalled AI adoption in this week’s pile: some things in your company were never filed as problems. You looked at them, decided that’s just how it is, and stopped — not because they didn’t hurt, but because nothing existed that could fix them. Those are the ones worth finding now. And a problem list won’t surface them, because that list was pruned years ago by what was possible then.

So the first step of Shukla’s POWER framework is not “problems” — it’s possibilities. Go work out what AI actually does — which he boils down to three verbs: understand, transform, generate — then look at competitors, your industry, and the one next door, and build a running list of what people are pulling off. On the whiteboard in the interview (captions confirm the moment: he writes POWER at the board around the sixteen-minute mark, after walking through a Discovery → Delivery → third-phase arc), the possibilities exercise comes before any roadmap — including the n8n workflows and the “hack the whole process” demos that follow. Possibilities first, then problems worth solving, then the rest of the letters.

“Adoption is whether your team uses AI. Advantage is whether the business gets anything back.”— Aakash Gupta, on Shukla’s framework

The distinction most companies mash together is the one to underline: adoption is not advantage. Plenty of companies have solved the first — the team uses AI — and quietly assumed the second followed. It didn’t. And there’s a side benefit to the possibilities map that has nothing to do with AI strategy: when a CEO says everything can be done with AI and the team knows it can’t, that argument is really about what each side believes is possible. Map that first, and the argument mostly disappears. The interview frames the whole thing as the roadmap to the quarter-million-dollar product-builder role — “is the role real or hype,” “what a product builder does,” “why delivery was the gate” — but the framework travels further than careers: it’s a way to find the work that was never filed as a problem.

Learnings

  • Start with possibilities, not problems. The problem list was pruned by old constraints; map what AI can do (understand, transform, generate) first.
  • Separate adoption from advantage. Team usage is not business return. Measure the second, not just the first.
